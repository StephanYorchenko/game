# Причинные цепочки реакций

Идентичность способности — общий `definitionId` независимо от владельца и экземпляра
(решение автора 05.11). `ExecutableEffect.cause.definitionIds` содержит причинных предков
запланированного эффекта. Перед его исполнением очередь проверяет отсутствие собственного
ID в этом списке, затем создаёт активную копию с добавленным ID. Поэтому A → A и A → B → A
обрываются, а B и C после A остаются разрешены. Жизнь владельца проверяется отдельно.

`trigger_reaction` — декларативная операция с target и одной из четырёх боевых фаз:
ATTACK_SUCCESS/FAILURE, DEFENSE_SUCCESS/FAILURE. Она копирует текущий LIFO-стек указанного
владельца и сохраняет исходный семантический контекст атаки, включая клетку и damageEventId.
Копии исполняются после всего породившего эффекта. DEATH нельзя вызвать этой операцией:
её назначает только граница смерти. Операция не создаёт атаку/броски сама по себе.

Обе очереди операций и CELL_DAMAGE наследуют ancestry для последствий. Событие урона
само не добавляет definitionId: оно переносит цепочку к порождённым DEATH-эффектам.
SUMMON и последствия смерти также сохраняют цепочку. Числовой модификатор не является
способностью и не получает ancestry. Журнал отмечает пропуск как `reaction_cycle`.

Каждый потомок получает независимую JSON-копию цепочки. Соседние эффекты одного фазового
снимка не отмечают друг друга выполненными. Два экземпляра одной способности, не являющиеся
предками друг друга, могут исполниться оба. Независимые атаки/обычные входы в фазу начинают
новую пустую цепочку; глобального набора «уже использованных способностей» и лимита глубины нет.
Постоянные экземпляры хранилища не получают ancestry от своих запланированных копий.

`enterReaction`, `copyReactionCause`, `inheritReactionCause` доступны для интеграций.
Сохранённая очередь должна сохранять cause вместе с записью; не сбрасывать его при
планировании дочерней реакции. Это ограничение причинной ветви, а не запрет всех ответных
эффектов, не общее ограничение числа атак и не автоматический триггер on_damaged.
