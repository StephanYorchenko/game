# Процесс разработки DeathWarriors

## Источники и задачи

- Правила игры: `spec/game-rules.md`. `CONFIRMED` — согласованные правила; `OPEN` и `DESIGN` не считать утверждённым геймплеем.
- Задачи: [доска DeathWarriors](https://trello.com/b/Y3cnmE6T/deathwarriors). Идентификатор задачи берётся из заголовка карточки, например `ENG-01`.
- Зависимости оформлять чек-листом **«Блокеры»**: каждый пункт — ссылка на блокирующую задачу. Для объединения задач использовать метку, без отдельных карточек-эпиков.

## Порядок работы

1. Выбрать доступную задачу и переместить её в **«грумминг»**. Прочитать описание, критерии готовности и чек-лист «Блокеры».
2. Если вопросы, мешающие реализации, закрыты и необходимые изменения блокирующих задач уже доступны в актуальном `master`, переместить задачу в **«In work»**. Иначе зафиксировать конкретный блокер и перейти к другой доступной задаче.
3. Обновить сведения об удалённом репозитории через `git fetch origin`. Создать новую ветку **от актуального `origin/master`**, сохраняя чужие незакоммиченные изменения.
4. Реализовать только выбранную задачу. При необходимости разделить изменения на атомарные коммиты. Проверить поведение и выполнить относящиеся к изменению проверки.
5. Запушить ветку и открыть PR в **`master`**. В описании кратко указать, что изменилось, зачем и как проверено; добавить ссылку на карточку.
6. Добавить ссылку на PR в карточку и переместить её в **«Review»** — это стадия код-ревью на доске. Перейти к следующей доступной задаче.
7. Продолжать, пока остаются задачи, реализуемые без участия автора. **Не сливать PR самостоятельно** и не считать задачу в Review снятым блокером. Если все оставшиеся задачи заблокированы, сообщить об этом со ссылками на ожидающие ревью PR.

## Ветки и коммиты

Ветка: `<feat|fix|chore|refactor>/<номер-задачи>-<краткая-тема>`.

Примеры: `chore/eng-01-game-core`, `feat/eng-03-seeded-rng`.

Коммит: `<feat|fix|chore|refactor>: <номер задачи> <коротко по-русски что изменилось>`.

Пример: `chore: ENG-01 добавлены сборка и проверка типов`.

Не добавлять указание соавторства с ассистентом и трейлеры `Co-authored-by` об ассистенте.

## Границы решений

- Репозиторий организован как **pnpm workspaces**. Модули размещаются в `packages/*`, игровое ядро — в `packages/game-core`. Использовать закреплённую в `package.json` версию pnpm, один `pnpm-lock.yaml` и `workspace:*` для внутренних зависимостей.
- В игровом ядре использовать **вертикальные слайсы по логическим доменам**: `src/<domain>/` содержит реализацию, тесты `*.test.mjs` и `README.md` этого домена. Не создавать общие слои `test/` или `docs/` для доменной логики. Публичный вход домена — `index.ts`; связанные части одного домена могут иметь отдельные файлы внутри его папки. Новую логику размещать в соответствующем домене, новый домен создавать по той же схеме.
- Сохранять публичные импорты пакета при перемещении внутренних файлов. Тесты домена проверяют публичный API; Node.js API в тестах не входят в собираемую реализацию ядра. После изменения структуры проверять чистую сборку без старого `dist/`.
- Перед PR выполнить `pnpm check` из корня. Игровое ядро не зависит от DOM, React, Phaser и Node.js API; инструменты и тесты могут использовать Node.js.

- Локальные технические решения принимать в рамках задачи и объяснять в PR, когда они существенны для ревью.
- Оставшиеся частные несостыковки правил решать на конкретных сценариях в соответствующем PR; не возобновлять предварительный опрос всех крайних случаев.
- Изменение согласованного геймплея выносить явно на согласование. Не подменять им техническое уточнение.
- До начала разработки очередной задачи проверять актуальность `master`, статусы блокеров и новые указания пользователя.
